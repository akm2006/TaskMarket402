## Role In TaskMarket402

x402 is the payment protocol for specialist-agent paid resources. The Manager Agent should be able to request a resource, receive a `402 Payment Required` response, satisfy payment through the payment adapter, and receive output.

## Current API Shape Summary

- x402 uses HTTP `402 Payment Required` to tell a buyer or agent that a resource requires payment before it can be returned.
- x402 V2 uses three standard headers:
  - `PAYMENT-REQUIRED`: server-to-client Base64 JSON payment requirement data.
  - `PAYMENT-SIGNATURE`: client-to-server Base64 JSON payment payload.
  - `PAYMENT-RESPONSE`: server-to-client Base64 JSON settlement feedback.
- Normal buyer flow:
  1. Client requests paid resource.
  2. Server returns HTTP 402 with payment requirements.
  3. Client prepares a signed payment payload from the requirements.
  4. Client retries with `PAYMENT-SIGNATURE`.
  5. Server verifies and settles payment locally or through a facilitator.
  6. Server returns the resource and a `PAYMENT-RESPONSE` header.
- Normal seller flow:
  - Define payment requirements: resource description, accepted scheme, price, network, asset, and pay-to address.
  - Reject unpaid requests with HTTP 402.
  - Verify/settle paid requests before returning the resource.
- Next.js seller docs currently recommend `withX402` for individual API route handlers because it settles only after a successful route response.
- Buyer docs currently reference `@x402/fetch`, `@x402/axios`, `@x402/evm`, and signer setup. Real buyer flow requires a wallet signer and funds.

## Phase 8 Multi-Agent x402 Shape

Phase 8 keeps the Phase 5 server-only buyer authority and upgrades the other two self-owned specialist-agent API routes to the same real x402 boundary. This is not user-delegated spend yet; MetaMask permission authority, ERC-7710 redemption, and 1Shot relay/status are separate later phases.

### Exact Flow

For each specialist agent (`contract_scanner`, `wallet_behavior`, and `market_context`):

1. Runtime requests the agent API route.
2. If that agent is configured for real x402, the route is protected with `withX402`.
3. Unpaid requests return HTTP 402 plus the SDK-managed payment requirement headers/body.
4. The server-only buyer adapter uses `@x402/fetch` and an EVM signer to satisfy the x402 challenge.
5. The route runs the self-owned specialist agent only after x402 verification/settlement succeeds.
6. Runtime records only sanitized payment states:
   - `real_x402_payment_required`
   - `real_x402_paid`
   - `real_x402_failed`
   - `real_x402_unavailable`
7. If config, facilitator, route, or settlement fails, runtime shows the explicit real x402 failure/unavailable state and falls back to the existing simulated/dev path without claiming real settlement.

### Implementation Boundaries

- Reuse the Phase 5 `@x402/next`, `@x402/core`, `@x402/evm`, and `@x402/fetch` packages.

## Phase 5 Contract Scanner Golden Path Plan

Phase 5 should replace only the Contract Scanner simulated proof with one real x402 payment flow. Wallet Behavior and Market Context should remain on the Phase 4 simulated/dev payment path.

### Exact Flow To Implement

1. Manager runtime requests the Contract Scanner paid API route without a payment signature.
2. Contract Scanner seller route is protected with x402 and returns HTTP 402 plus `PAYMENT-REQUIRED` when unpaid.
3. Server-side buyer adapter uses `@x402/fetch` with an EVM `exact` scheme signer to parse the challenge, create the payment payload, and retry with `PAYMENT-SIGNATURE`.
4. x402 seller route verifies and settles through a facilitator.
5. Contract Scanner handler runs only after valid payment verification and successful route execution.
6. Response includes `PAYMENT-RESPONSE`; runtime records the real x402 payment state, then returns the typed Contract Scanner output.
7. Wallet Behavior and Market Context continue through simulated/dev flow until later phases.

### Package Shape To Use

- Seller/API route:
  - `@x402/next`
  - `@x402/core`
  - `@x402/evm`
- Buyer/runtime:
  - `@x402/fetch`
  - `@x402/core`
  - `@x402/evm`
  - existing `viem` for `privateKeyToAccount`

The Phase 5 implementation installed only these needed x402 packages.

Use a dedicated throwaway Base Sepolia buyer wallet with only testnet USDC and minimal testnet ETH. Store the private key only in `.env.local` or deployment secrets. Never expose it to the client, logs, `PAYMENT-RESPONSE`, or WorkGraph DTOs.

CDP non-custodial wallet is also documented and may be safer long term, but it introduces CDP wallet secrets and SDK scope. For the smallest Phase 5 slice, use a throwaway local EVM private key on Base Sepolia.

- Package API drift: inspect installed `@x402/*` types after package install before coding.

## Phase 4 Implementation Shape

Phase 4 is not a real x402 integration. It implements an x402-style development boundary so specialist agents behave like paid HTTP resources before MetaMask, ERC-7710, 1Shot, wallet signing, and real settlement are added.

- Request without an accepted development proof returns an HTTP 402-style challenge.
- Challenge response includes `PAYMENT-REQUIRED` with Base64 JSON and a sanitized JSON body.
- Request with accepted development proof returns the specialist-agent output.
- Successful response includes `PAYMENT-RESPONSE` with Base64 JSON marked as simulated settlement.
- UI/runtime labels must say `x402-style dev payment flow` or `simulated settlement`.
- No `@x402/*` package is installed in this phase.
- No facilitator call, wallet signature, private key, ERC-7710 execution, MetaMask permission, 1Shot relay, or onchain settlement is implemented.

## Env Vars

- `X402_DEV_MODE`: optional server-side flag for the simulated Phase 4 flow. Use `true` locally.
- `X402_DEV_PAYMENT_PROOF`: optional local-only development proof string. This is not a real payment secret and must not be treated as settlement.
- `X402_PAY_TO_ADDRESS`: future real seller address; not used for real settlement in Phase 4.
- `X402_SETTLEMENT_NETWORK`: future real x402 network value such as `eip155:84532`; Phase 4 can use it only in simulated challenge metadata.
- `X402_FACILITATOR_URL`: future facilitator URL; not called in Phase 4.
- `USDC_CONTRACT_ADDRESS`: future payment asset address; Phase 4 can use it only in simulated challenge metadata.

## Phase 4 Fallback Behavior

- Missing payment proof: return 402-style `payment_required`.
- Invalid development proof: return 402-style safe failure; do not echo proof values.
- Accepted development proof: return typed specialist output and `dev_payment_accepted`.
- Agent/data-source fallback after accepted proof: return the fallback specialist output; payment acceptance does not imply data quality.
- Real x402 settlement failure categories are not modeled yet because no settlement occurs.
